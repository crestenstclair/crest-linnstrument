# Firmware provenance and simulation

Upstream: https://github.com/rogerlinndesign/linnstrument-firmware
Pinned commit: `54bb1c9d355b1075b474ade0a0246b80ff7f3524` (firmware 2.3.4 build .074).
The submodule stays unmodified. The native build applies three reviewable portability patches:

- `0001-const-font-lookup.patch` makes two lookup pointers const for desktop C++.
- `0002-calibration-neighbor-bound.patch` bounds the Y interpolation neighbor by the
  active geometry. Upstream hardcodes nine calibration columns; the 128 fixture initializes
  six. At physical column 16 the absent right neighbor has zero interpolation weight, but
  upstream still evaluates its zero denominator. The pinned ARM ELF uses `sdiv` here;
  native x86 division faults, while Apple ARM64 silently returns zero. Skipping the unused
  neighbor preserves the intended interpolation and avoids C++ undefined behavior.
- `0003-touch-neighbor-bounds.patch` prevents slide/expression probes beyond the active
  surface. UBSan found an out-of-bounds `touchInfo[26]` read at the 200's right edge.
  Missing neighbors now contribute no slide or pressure; valid neighboring cells use the
  original firmware path. This replaces undefined memory reads, not measured hardware
  behavior. Physical edge behavior and full ARM/native trace equivalence remain unqualified.

## Reproduce builds

```sh
git submodule update --init
python3 scripts/build-arm.py
scripts/build-native.sh
python3 scripts/test-firmware.py
# Optional diagnostic build; CI runs this as well as the normal worker.
scripts/build-native.sh --sanitize
python3 scripts/test-firmware.py
```

The ARM recipe downloads checksum-pinned Arduino CLI 1.3.1 and installs SAM 1.6.11,
including upstream's GCC 4.8.3-2014q1. It builds unmodified firmware for `arduino_due_x`.
Local reproduction used 163,828 bytes of program storage. This reproduces the ARM build
with the original SAM/compiler pair; it does not claim byte identity with Arduino IDE 1.8.1.
Old tool executables may require Rosetta on Apple Silicon or 32-bit libc on Linux.

Arduino preprocessing is explicit: `generate-sketch.py --extract` extracts declarations
from the actual ARM build's sketch translation unit. Committed `prototypes.inc` permits
native builds without Arduino or an ARM compiler. The normal generator concatenates the
main sketch, declarations, and alphabetically sorted sketches reproducibly. CI verifies
regeneration. Production Rust builds require none of this tooling.

Desktop flags are C++17, `-fwrapv -fshort-enums -funsigned-char`. A lexical generated-source
pass maps SAM `long`/`unsigned long` to explicit 32-bit types without changing comments or
strings. `arm-layout.inc` asserts 119 sizes, persisted-field offsets and char semantics,
derived independently from symbols in a GCC ARM layout probe. Pointer-bearing desktop
runtime structures are not flash interchange formats. Little-endian macOS ARM64 and Linux
x86_64 are the current native targets. Unsupported architectures are not qualified.

## Executed path

The worker calls upstream `setup()` and `loop()`. Contacts become raw ADC values returned
through SPI sensor-selection decoding. Upstream calibration, scanning, touch ownership,
MPE channel allocation and serial MIDI generation execute in upstream code, with the
documented boundary guards above. No normal contact
command can inject a note or write upstream touch objects. MIDI input goes through the
board Serial FIFO and upstream parser. LED frames integrate LED SPI writes and output enable,
including column multiplexing and firmware pulse/brightness patterns.

The native compatibility services model:

- A 64-bit scheduler with wrapping 32-bit Arduino clocks. Each `micros`, `millis`, serial
  polling or SPI byte advances one synthetic microsecond; explicit delays advance time.
  Background work inside upstream busy loops therefore progresses. These are deterministic
  simulation costs, not measured CPU or bus latency.
- Both identities (200 and 128) via pin 38, GPIO modes, LED output enable, foot-switch input
  pins and presses, sensor/ADC SPI transactions, and strict errors on unsupported peripherals.
- Continuous X/Y/Z contacts, up to 16, with a flat-top horizontal footprint and overlap
  around cell boundaries. Vertical position is local to the nearest row. Sensor pressure
  is an ideal synthetic surface; calibration uses upstream default geometry. This model
  is neither measured sensor data nor proof of physical calibration or tactile response.
- Bounded serial FIFOs, UART byte-completion timestamps and output backpressure. This board
  serial model is separate from the optional OS MIDI transport. Unsupported serial diagnostics
  go to stderr, not MIDI or protocol output.
- A 256 KiB erased flash image, deterministic writes and persistent image save/reload.
  Writes currently model an aggregate 100 µs cost rather than electrical erase/program
  behavior. Ideal fixtures are generated by upstream settings/calibration routines before
  normal worker execution. They explicitly configure lower MPE and disable pitch quantization.
- The pinned ARM newlib `rand` recurrence, verified from its ARM object: a 64-bit state,
  multiplier 6364136223846793005, increment 1, high 31 bits. Seed is 1. A previous desktop
  generator must not be substituted, since arpeggiator/random display behavior would differ.

Generated fixture manifests contain firmware/build/patch hashes, geometry, MPE profile,
seed and flash SHA-256. The Rust bridge rejects wrong versions, geometry, flash hash or
simulator build. Each worker snapshot records firmware/build/patch identity and counters
for ADC, sensor selects and LED writes. The build hash covers sketch, shims, portability
patches, layout assertions and native build/generation scripts.

## Bridge and fixtures

Typed bridge commands include contact `{id,x,y,z,latched}`, contact-profile, release,
cancel-contact, release-momentary,
release-all, pause, step and reset. X centers run 0 through 25 (16 for the small model),
column 0 is the control column; Y centers run 0–7 from bottom; Z is 0–1. Nonfinite or
out-of-bounds input is rejected before contacting the worker. Mouse pressure is explicit.
The worker protocol is bounded line commands and JSON snapshots. `contact`, `release`,
`release_all`, `switch`, `midi`, `advance`, `snapshot`, and `save` are implemented commands.

The native bridge timestamps receipt with `Instant`. Its scheduler advances before applying
each received command; X/Y and target pressure are held until the next native update.
Optional linear pressure envelopes apply a 0–2 second attack/release, sampled every 1 ms
by this scheduler; zero is immediate. Moving an attacking finger preserves its current
pressure and retargets the remaining attack. Normal release uses the selected tail;
focus recovery, pointer cancellation, Release All, reset and mode changes bypass it.
At the 16-contact limit a new active finger retires the oldest released tail before any
active contact is rejected. This is synthetic contact behavior, not firmware voice stealing.
Trace commands contain the resampled sensor inputs, so replay follows the identical path.
Real-time catch-up is limited to 50 ms per wake; a stalled
host can run simulation behind wall time. Headless tests use explicit advances. A worker
loop can overshoot the requested endpoint by its current scan operation; actual snapshot
and MIDI byte timestamps remain authoritative. Browser polling only displays snapshots.

Display frames accumulate PWM exposure for at least 25 ms; requests without elapsed sensor
time retain the last decoded frame. The C++ worker responds in a separate process with a
five-second bridge watchdog. Worker death marks disconnected and releases host notes;
performance input never switches to a protocol generator. The scheduler remains available
for Reset and trace export; reconnect/reset preserves committed clips. Reset reloads the
selected fixture rather than claiming persistence of unsaved device settings.

`test-firmware.py` contains independent expectations for pitches 43/53/63 under the
fixture layout, member-channel separation, independent X/Y/Z changes, expression isolation,
continuous two-cell slides (pitch tolerance 20 bend units), release, microsecond wrap,
User Firmware Mode, coordinates and a red LED command round trip. It repeats complete
scenarios and compares ordered MIDI/LED snapshots. Captured traces under `target/` are
observations, not self-approved golden truth. Rust firmware integration separately checks
record/reopen/virtual-pad launch, independent live-plus-clip channels and the playing LED
decoded from hardware writes. Additional cases cover concurrent three-contact X/Y/Z, all
15 members plus the 16th touch, foot-switch sustain, persisted octave settings and erased
flash boot. Right-edge tests independently assert calibrated CC74 values and X/Z isolation
on both geometries. CI repeats the firmware suite with undefined-behavior checks enabled.
At capacity the pinned firmware rotates onto channel 2 without first releasing
the old note; the library explicitly rejects that ambiguous ownership. Contact placements
for capacity tests avoid the stock phantom-rectangle rejection rule.

Both geometries also exercise short-tap and >500 ms hold behavior on the actual octave
control column, select an octave through sensor contacts and verify return to ordinary
playing. Split acceptance configures seven lower and seven upper members through standard
RPN, enables a physical split through NRPN, and checks independent notes/expression with
a negotiated ±24-semitone range. This validates firmware split generation; the development
host still defaults to one lower input zone.

Manual gesture runs include the fixture manifest, initial snapshot, ordered worker commands,
MIDI bytes, LED changes and each complete snapshot hash. Replay boots the same worker and
fixture and checks every boundary. Runs are bounded to 50,000 commands and a conservative
16 MB recording budget (32 MB file limit). A full buffer rejects export rather than claiming
a complete run. The UI exposes capture/replay verification and separate raw firmware and
reallocated host output. This replay is determinism evidence; independent expected musical
behavior still comes from the acceptance tests. Local desktop mouse/keyboard testing
exported and exactly replayed a 1,267-step manual run.

## Binary feasibility and limits

Inspected QEMU 11.1.1 machine inventory: no SAM3X/Arduino Due board. Inspected Renode's
platform inventory at `4c0d973e83addd2d60b2d12139015fbb4a7fc7d0`: SAM4S boards exist,
no matching SAM3X/Due board found. Cortex-M3 support alone cannot execute this board image.
A binary-emulation workstream needs a Due memory/boot map plus correct PMC/PIO, USART,
SPI/chip selects, EFC/flash and board wiring; sensor, ADC and LED external peripherals are
still necessary. Existing Cortex-M/NVIC/SysTick and some SAM peripheral models may be reused,
but no boot claim or effort estimate is justified without a peripheral coverage prototype.

The required native path is now demonstrated. Remaining fidelity work includes complete control-panel/calibration workflows, all split
profiles, exhaustive slides/releases and long-run queue pressure. ARM/native execution
trace comparison, physical sensor measurements, USB behavior and Deck latency remain
unqualified. Do not describe native compilation as execution of the original ARM binary.

## Interactive scripted contacts

The instrument's built-in phrase and custom JSON scenarios use the same contact setter,
worker and scheduler as mouse/keyboard input. Version 1 scenarios contain geometry and
ordered relative microsecond times, with contact, release and release-all actions. The
entire scenario validates before execution: at most 4,096 steps, 60 seconds and 16 contacts,
with all contacts released by its end. File reads are capped at 1 MB. Scenario time follows
native firmware time; sensor-loop overshoot is retained, not concealed by frame timing.
Pause/single-step work during a script. A script owns contacts through their release tails;
manual contact edits/releases are rejected while it runs, and window focus does not cancel
it. Due envelope samples execute before a same-time script command; firmware scan overshoot
remains authoritative. Release All cancels future script steps. Reset and
mode changes cancel scripts and release contacts. Browser frames only render snapshots.

The bridge's 256-command queue has an independent overflow latch. If a release cannot be
queued, the scheduler discards stale gestures, silences allocated host/OS MIDI output,
clears contact/script/envelope ownership and reports disconnected. Reset is required before
accepting performance again. Worker failures use the same cleanup, including virtual-port
All Sound Off; no queued contact is replayed during reset.
